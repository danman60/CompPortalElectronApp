# R529 / R530 recovery — Sunday re-record chaos fix

**Date:** 2026-04-19
**Context:** During UDC London Day 3 (Sunday morning), R529 recorded successfully. Then R530 started recording while the app was still pointed at R529's slot, triggering the app's re-record flow: R529's processed outputs were archived to `_archive/v1/`, and R530's raw MKV was written at the top level under R529's filename. R530 was never given its own `media_packages` row. Only the raw MKV was generated for R530; no performance/judge MP4s or keyframes.

Downstream effects:
- **R529 DB row** has `has_perf_video: false` and a `video_start/end_timestamp` window (13:27:25 → 13:30:07 UTC) that's actually R530's recording window.
- **R530 DB row** does not exist.
- **Offset detector** on the later F:\ SD import saw this gap + window anomaly and derived a spurious `-201s` offset for P23 camera, mis-assigning ~4,298 photos.

## Execution order

### Phase 1 — R529 (fast path — files already processed)
1. SCP from DART: `529/_archive/v1/*.mp4` and `529/_archive/v1/keyframes/*.webp` → SpyBalloon `/tmp/r529-recovery/`.
2. Upload to R2 under R529's entry_id path with normalized filenames (`performance.mp4`, `judge1.mp4`, etc.).
3. UPDATE `media_packages` for R529: set `video_start/end_timestamp` to corrected values + set `performance_video_url`, `judge{1,2,3}_video_url`, `video_keyframes`.

### Phase 2 — R530 (re-process MKV)
4. SCP from DART: `529/529_*.mkv` (top-level) → SpyBalloon `/tmp/r530-recovery/source.mkv`.
5. ffmpeg smart-encode (matches app's pipeline):
   - `libx264 -preset fast -crf 23` video pass → `_temp_video.mp4`
   - Mux `_temp_video.mp4` with each audio track → `performance.mp4`, `judge1.mp4`, `judge2.mp4`, `judge3.mp4` (each `-c:v copy -c:a aac -b:a 128k`)
6. Extract 3 keyframes at 20/50/80%, 400×400 WebP, `-q:v 5` → `keyframes_keyframe_{0,1,2}.webp`.
7. Upload all R530 outputs to R2 under R530's entry_id path.
8. INSERT new `media_packages` row for R530: tenant + comp + entry_id, `status='complete'`, corrected window, all URLs, `photo_count=0` initially (realignment in Phase 3 may bring photos in).

### Phase 3 — Photo realignment (Sunday)
9. For all photos in `media_packages` rows with `entry_number BETWEEN 525 AND 560` (Sunday morning range):
   - Compute correct `media_package_id` by matching `captured_at` to the package whose window contains it.
   - If no window contains it (gap photo), assign to nearest package by min(|captured_at − video_start|, |captured_at − video_end|).
   - UPDATE `media_photos.media_package_id` where current != correct.
10. Refresh `photo_count` on affected packages via:
    ```sql
    UPDATE media_packages SET photo_count = (SELECT COUNT(*) FROM media_photos WHERE media_package_id = media_packages.id AND deleted_at IS NULL) WHERE competition_id=... AND entry_number BETWEEN 525 AND 560;
    ```

### Phase 4 — Detector state cleanup (deferred until after show)
11. Clear `state.cameraOffsets.P23 = -201000ms` from DART's persisted state. (Requires DART write — wait for operator go-ahead after show.)
