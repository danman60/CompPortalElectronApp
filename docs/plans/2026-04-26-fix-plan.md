## Executive summary (60-second read)

1. **The headline failure was silence, not the cliff.** Photo ingest broke at 09:04 EDT and was not detected until 18:25 EDT — 9h21m of zero alerts on either CSE or CompPortal while `machine_logs` had 5 `MISSING_PHOTOS_DETECTED`, 21+ UDP timeouts, 1500+ ENOENT retries, 158 dayChecklist module errors. Detection has to ship before correctness, because even a perfect new pipeline can break and we already proved nobody was watching.
2. **Phase 1 (Detection & Escape valves) lands first** so the next failure cannot stay silent past one routine cycle: two-surface no-flow banner (CSE app + CompPortal CD), manual "Reconcile cards" button (operator's lunch-break safety net), job-queue bulk-prune IPC + UI (kill the cascade), the lying-success toast fix, a **simple "Clear queue" button + opt-in clear-on-startup setting** (item 1.6 — prevents stale queued jobs from poisoning post-event manual fixes), and **scratch-status sync to CompPortal** (item 1.7 — operator escalation 2026-04-27 12:23: CSE-side scratched routines now propagate to CD / parent / livestream / Verify-Media / no-flow banner, so they no longer sit as "media pending" forever). This is mostly additive UI; small blast radius.
3. **Phase 2 (Watermark-driven import + manual-import parity + strict-matcher invariants) kills the cliff at the root** by replacing the broken `<2/3 today` pre-check with a persisted, per-(volume-serial, body-key) watermark, generalising the camera body-key regex to recognise NAP_/Q53A/Pxx (today's `NAP_*.JPG` photos lived in the `_unknown` bucket where every per-camera path was silently inert), persisting watermark advances on every file (not end-of-import), routing the manual `PHOTOS_IMPORT` IPC through the same watermark/dedup path it currently bypasses (per L3), **enforcing the strict one-photo-one-routine business rule at both matcher level and DB level via a partial unique index on `(competition_id, camera_body, filename, captured_at)`** (item 2.7 — operator-asserted invariant 2026-04-27), and **preserving every take's recorded window as immutable so photos relink correctly across re-records and extras** (item 2.8 — operator escalation 2026-04-27).
4. **Phase 3 (NORTH STAR UX surface)** delivers the operator's contract verbatim: top-left chip during import, top-left "Card safe to remove" toast on completion, no center-screen modals, round-robin slideshow scatter, and re-introduction of the silenced clock-mismatch / date-mismatch warnings as escalating banners (suppressed-without-escalation = silence).
5. **Phases 4 & 5** are second-class-of-failure (re-record drama, Phase 1 of the rerecord-redesign — non-schema UX cleanup) and the long tail (timezone contract for manual scripts, asar packaging fixes, audio/UDP/heartbeat health surfaces, R2 storage reconciliation). These ship after the photo-import contract is bulletproof.

> **OPERATOR ESCALATION (added 2026-04-27 10:45 EDT):** Re-recording into a slot, and recording extras, is *currently* breaking photo matching badly — every event so far has produced a multi-hour post-show DB cleanup pass for displaced photos. The matcher only knows the *current* routine's window, so when a re-record overwrites `recordingStartedAt` (verified at `recording.ts:860-862`), the prior take's window is lost and any photo that fell in it ends up unmatched, mis-attributed to a neighbour, or silently linked to the new take's slot. **This cannot wait for redesign Phase 2's full schema work.** Item **2.8 (Immutable take-windows + take-aware matcher)** is added to Phase 2 as a P0 to deliver the *correctness* part of redesign invariants 2 + 3 + 5 with the smallest possible blast radius — without waiting for the sibling-takes schema, the row inspector, or the new modals.

> **OPERATOR ESCALATION (added 2026-04-27 10:51 EDT) — STRICT INVARIANT:** *"A photo should only ever exist in one routine as it was taken during that routine and couldn't be taken at two different routine times. If the matching logic is assigning it to two routines then there's something off about the timestamps."* This is **grounded business logic, not a heuristic.** A physical camera shutter clicked once at one moment in time; the photo belongs to whichever routine was being performed at that moment, and to no other. Any duplication in `media_photos` with the same `(camera_body + filename + EXIF capture_time)` linked to two `media_package_id`s is a bug — most likely caused by routine windows that overlap, are wrong, or are mutated by re-record (which is exactly what item 2.8 fixes). Item **2.7 is upgraded from "investigate" to "enforce as a hard invariant"**: matcher-level + DB-level uniqueness, with cross-attribution treated as a bug to be quantified and zeroed. The full enforcement story is documented in 2.7 below.

> **OPERATOR ESCALATION (added 2026-04-27 12:01 EDT, clarified 12:05 EDT):** *"We need the queue cleared, or a way to clear the queue on startup, so we don't have poisoning when a lot of post-event fixes are made."* The CSE app's local job queue (`userData/job-queue.json`) survives across app restarts (verified at `jobQueue.ts:58-87` — load-from-disk + reset-running-to-pending). After a live event, the operator typically does a round of manual post-event fixes (Python upload scripts, direct Supabase INSERTs, R2 reconciliation). The dormant jobs in `job-queue.json` from the event can later wake up — on the next boot, on auto-retry, on operator clicking Retry — and run against now-out-of-date paths and payloads, potentially duplicating rows or overwriting DB-side fixes. The narrow ask is a **queue-clearing escape valve** so the operator can wipe stale jobs before they poison anything. Item **1.6 (Queue clear + clear-on-startup option)** is added to Phase 1.

> **OPERATOR ESCALATION (added 2026-04-27 12:23 EDT):** *"If a routine is SCRATCHED in elec app we want it to be marked SCRATCHED in media portal."* Verified: `RoutineStatus` includes `'scratched'` (`types.ts:13-16`); `state.scratchRoutine()` at `state.ts:932-943` sets status locally and clears recording fields; *no plugin endpoint in `upload.ts` notifies CompPortal of scratch*. ## Phase ordering — why detection ships before correctness

Both Phase 1 (Detection & Escape valves) and Phase 2 (Watermark Import) are P0. They could ship in either order. We ship Phase 1 first because:

1. **Today's headline failure was 9-hour silence.** The cliff was recoverable in 5 minutes once anyone noticed; the silence multiplied the cost by 100×. Detection is the higher-leverage fix.
2. **Phase 1 is a backstop that catches Phase 2 bugs.** Even with the watermark path live, *something* in the pipeline can break — R2 throttling, plugin auth expiring, camera-clock drift exceeding gate, network outage. The banner catches all of them. The banner is also the catch for the things we haven't thought of.
3. **Phase 1 has smaller blast radius.** Adding a header banner + an IPC-triggered manifest scan is additive UI. Replacing the import path is invasive — anything that touches `photos.ts` has to be re-validated against the existing matcher, dedup, offset detector, and TZ paths.
4. **Phase 1 unblocks operator confidence in Phase 2.** With the banner + reconcile button live, the operator will *see* Phase 2 working in real time at the next live event. Without them, Phase 2 ships into the same observability vacuum that hid today's failure.
5. **Phase 1 is mostly portable.** The Reconcile button in particular is independent of the auto-import path entirely — operator can run it with or without Phase 2.

If forced to pick, ship the Reconcile button (1.2) and the lying-toast fix (1.3) first — they're 1-2 day work each and immediately net-positive. The full no-flow banner (1.1) is a week of work split across CSE + CompPortal. Phase 2.1 watermark is 1-2 weeks. Phase 2 should not ship before Phase 1.1 + 1.2 + 1.3 + 1.4 are all live.

# PHASE 1 — DETECTION & ESCAPE VALVES

**Goal:** make today's class of failure (silent ingest break + cascading queue saturation + lying success toasts) impossible to remain undetected past one routine cycle. Operator and CD must each have an independent surface that screams when photos stop flowing.

**Ship order within phase:** 1.3 → 1.5 → 1.4 → **1.6** → **1.7** → 1.2 → 1.1 → **1.8** → 1.1b. (Smallest, most-isolated wins first. 1.6 ships right after 1.4 because they share the same admin panel UI and `jobQueue.ts` helpers; bundle the work. **1.7 ships before 1.1b because the no-flow banner depends on scratch awareness — without 1.7, the banner false-positives on consecutive scratches.** 1.8 wires into 1.1's banner component, so it ships after 1.1.)

**Phase exit signal at next live event:** within 30 minutes of any photo-ingest break, *one of* (a) the CSE banner is visible, (b) the CD dashboard banner is visible, (c) the operator runs Reconcile and sees a non-zero "missing on card" count. **None of these existed today.** Additionally: between events, operator can clear the queue (manually or via the startup toggle) so dormant jobs don't poison post-event manual fixes.

## 1.1 — CSE app no-flow banner [CSE]

**What:** Persistent header banner (NOT a toast) that fires when *both* of:
- Last N completed routines (default `N=3`) have `photo_count = 0` *and*
- No successful import has completed in last `M` minutes (default `M=15`)

When triggered:
- Banner colour-grades yellow → red over time (yellow at trigger; red after `2M` minutes elapsed without resolution).
- Body text: *"No photos imported in last {M} min. Last successful import: {HH:MM EDT}. Last card detected: {HH:MM EDT}."*
- Inline buttons: **[Run Reconcile]** (kicks off Phase 1.2 button), **[Acknowledge — Reason]** (dropdown: *camera being repositioned* / *photographer on break* / *drone shot only* / *false alarm*), **[Open log]**.
- Auto-clears when photos resume flowing for 1 routine.
- Acknowledge sets a per-comp suppression with the chosen reason recorded into `machine_logs` and a 30-min auto-expire.

**Where:**
- New file `src/main/services/photoFlowMonitor.ts` — subscribes to `events` (existing event bus), evaluates the trigger condition every `routine.completed` event + on a 60s tick.
- IPC channel addition to `src/shared/types.ts` near line 659 (where `DRIVE_MISSING_PHOTOS_DETECTED` lives): `PHOTO_FLOW_ALERT: 'photo:flow-alert'`, `PHOTO_FLOW_ALERT_ACK: 'photo:flow-alert-ack'`.
- New renderer component `src/renderer/components/PhotoFlowBanner.tsx`, mounted in `src/renderer/components/Header.tsx` (uses existing `useImportMinimizedState` neighbourhood).
- `MISSING_PHOTOS_DETECTED` (already emitted at `driveMonitor.ts:507-510`) becomes one of the trigger inputs — merge of P1.2 into this item.

## 1.6 — Queue clear + clear-on-startup option [CSE]

**Operator clarification 2026-04-27 12:05 EDT:** *"We need the queue cleared, or a way to clear the queue on startup, so we don't have poisoning when a lot of post-event fixes are made."*

**Scope:** narrow. This item is *not* a sweeping reconciler rewrite or app-state-vs-DB-state arbitration. The narrow risk: between events, the operator does manual recovery work in the DB; meanwhile, jobs from the prior event sit dormant in `userData/job-queue.json`. On next app boot, those jobs can wake up and run against stale paths/payloads, poisoning the DB-side recovery work. Give the operator a simple way to wipe the queue on demand and on startup.

**What 1.6 adds:**

### A. Manual "Clear queue" action

A simple **"Clear queue"** button in the same admin panel as item 1.4's bulk-prune controls. On click:
1. Preview: *"Clear all {N} queued jobs? This removes pending, failed, and quarantined jobs. Running jobs are not affected. The DB is unaffected."*
2. Operator confirms → all jobs in `pending`, `failed`, `quarantined` state are removed; `running` jobs are left alone (they finish or fail naturally).
3. Logs `JOB_QUEUE_CLEARED: removed=N kept_running=M` to `machine_logs`.

This is a thin wrapper over item 1.4's `JOB_QUEUE_PRUNE_QUARANTINED` plus equivalent prunes for `pending` and `failed`. From an implementation standpoint it's the most blunt of the prune actions — "wipe everything not actively running."

### B. "Clear queue on startup" setting

A toggle in app settings: **"Clear pending job queue on startup"** (default: OFF).

When ON:
1. On every app boot, before the queue loads from disk into memory, the boot path empties `userData/job-queue.json` of all `pending`/`failed`/`quarantined` entries.
2. Logs `JOB_QUEUE_CLEARED_ON_STARTUP: removed=N` to `machine_logs`.
3. Default OFF so it doesn't surprise operators who expect the queue to survive a restart mid-event.

When OFF (default):
- Existing behaviour at `jobQueue.ts:58-87` preserved: load from disk, reset `running` → `pending`, continue.

The toggle is the operator's "set this between events" knob. Flipped ON post-event, the next boot is clean. Flipped OFF before the next event, the queue persists normally.

### C. Optional: stale-job auto-prune on boot

Lower-priority sub-feature, can ship in a follow-up: on every boot, prune jobs that are older than N days (default 7) AND in non-terminal state (i.e. they've been dormant for more than a week). Log `JOB_QUEUE_STALE_AUTOPRUNED: removed=N older_than=Ndays`. This catches the "operator forgot to clear before the next event" case.

If the auto-prune happens on a job whose DB target is already correctly filled, the operator never sees a problem. If on a job whose DB target genuinely needs uploading, the operator can re-trigger via Reconcile (item 1.2) — which is the right flow for "a week-old upload didn't land, what's the truth?"

**Where:**
- `src/main/services/jobQueue.ts` — three new exported functions:
  1. `clearAll(opts: {keepRunning: boolean}): number` — drops jobs in `pending`/`failed`/`quarantined`; respects `keepRunning` flag (default true).
  2. `clearOnStartup()` — called from the app boot path before `load()` runs; reads-then-writes `job-queue.json` to drop pending/failed/quarantined entries.
  3. `pruneStale(olderThanDays: number)` — for sub-feature C.
- `src/main/ipc.ts` — new `safeHandle(IPC_CHANNELS.JOB_QUEUE_CLEAR_ALL, ...)` near the existing `JOB_QUEUE_*` handlers (lines 1177–1216).
- `src/shared/types.ts` — new IPC channel constant near line 731–736: `JOB_QUEUE_CLEAR_ALL: 'job:queue-clear-all'`.
- Settings shape: extend `AppSettings.behavior` (or wherever the related toggles live) with `clearJobQueueOnStartup: boolean`, defaulted false.
- Boot path: in `src/main/index.ts` (or wherever app init happens), check the setting; if true, call `clearOnStartup()` *before* `jobQueue.load()`.
- Renderer: extend item 1.4's admin panel (`JobQueueAdmin.tsx`) with a new "Clear queue" button (largest, blunt) alongside the prune-by-status / prune-by-prefix / prune-by-error variants. Also add the settings toggle to wherever app settings are surfaced.

**Why:** **operator clarification 2026-04-27 12:05 EDT.** Solves the narrow problem (stale jobs poisoning the DB after manual recovery) with the smallest change that gives the operator full control: one button + one setting. The bigger reconciler-rewrite ideas from earlier drafts are intentionally not in this item — they were over-engineered for what the operator actually needs.

**Risk + mitigation:**
- *Risk: operator flips "clear on startup" ON during a live event and loses the queue across a crash-restart.* → Mitigation: setting is OFF by default. Tooltip on the setting explains "use between events, turn off during live work."
- *Risk: "Clear queue" mid-event accidentally drops in-flight retries.* → Mitigation: confirmation dialog + the action only touches non-running jobs. `running` jobs are left alone.
- *Risk: legitimately-pending jobs (e.g. mid-upload uploads waiting their turn) get cleared.* → Mitigation: that's the operator's call to make. The button shows a count + breakdown so they know what's being cleared. If they cleared something they shouldn't have, item 1.2 (Reconcile cards) re-establishes truth.
- *Risk: auto-prune (sub-feature C) drops a job whose DB target genuinely needs uploading.* → Mitigation: ship A and B first; treat C as a follow-up that's only enabled after we have a few events of confirmation that A+B cover the real-world workflow.

**Testable signal at next live event:**
- Pre-event: open admin panel, confirm "Clear queue" button is visible, confirm setting "Clear job queue on startup" exists in settings.
- Post-event recovery: operator runs Python recovery scripts to fix gaps in DB. Local queue still has N stale jobs.
- Operator clicks **Clear queue**. Preview says "Remove N jobs (P pending, F failed, Q quarantined)." Confirm. Queue is empty. `machine_logs` has `JOB_QUEUE_CLEARED: removed=N kept_running=0` entry.
- (Alt) Operator flips "Clear queue on startup" ON, restarts the app. Boot log shows `JOB_QUEUE_CLEARED_ON_STARTUP: removed=N`. Queue is empty. Operator flips setting OFF before the next live event.

- If the share code isn't resolved (offline / pre-resolve), the job sits in queue and runs once the connection lands.

### C. Downstream surfacing in CompPortal

1. **Parent media portal**: hide "media pending" / show a small "Routine scratched" pill instead of the missing-media placeholder.

## 2.2 — Generalise camera body-key regex [CSE]

**What:** `getCameraBodyKey()` at `photos.ts:254-258` matches only Lumix `^(P\d{2})\d{5}\.(?:jpg|jpeg)$`. Replace with a multi-prefix lookup table (per the original prompt's example):

```typescript
type CameraBodyKey = { prefix: string; format: RegExp; bodyKeyExtractor: (m: RegExpMatchArray) => string }

const BODY_KEY_PATTERNS: CameraBodyKey[] = [
  // Lumix Pxx — existing
  { prefix: 'P', format: /^(P\d{2})\d{5}\.(?:jpe?g)$/i, bodyKeyExtractor: m => m[1].toUpperCase() },
  // Nikon NAP_NNNN, NAP_NNNNN
  { prefix: 'NAP_', format: /^(NAP)_\d{4,5}\.(?:jpe?g)$/i, bodyKeyExtractor: m => 'NAP' },
  // Canon Q53A NNNN (sometimes Q63A, Q73A — the 1st char after Q is body-id)
  { prefix: 'Q', format: /^(Q\d{2}[A-Z])\d{4}\.(?:jpe?g)$/i, bodyKeyExtractor: m => m[1].toUpperCase() },
  // Generic Canon IMG_, DSC_, _MG_ for fallback
  { prefix: 'IMG_', format: /^(IMG)_\d{4,5}\.(?:jpe?g)$/i, bodyKeyExtractor: m => 'IMG' },
  { prefix: 'DSC_', format: /^(DSC)_\d{4,5}\.(?:jpe?g)$/i, bodyKeyExtractor: m => 'DSC' },
]

export function getCameraBodyKey(filePath: string): string | null {
  const base = path.basename(filePath)
  for (const p of BODY_KEY_PATTERNS) {
    const m = base.match(p.format)
    if (m) return p.bodyKeyExtractor(m)
  }
  return null
}
```

## 2.7 — One-photo-one-routine: enforce as a hard invariant [CSE+CP]

**Operator escalation 2026-04-27 10:51 EDT — strict business rule:** *"A photo should only ever exist in one routine as it was taken during that routine and couldn't be taken at two different routine times. If the matching logic is assigning it to two routines then there's something off about the timestamps."*

**Origin:** post-mortem **L1** — *"4,519 filenames found in multiple routine folders. The `_dupN` suffix wasn't the only bug — there's matcher multi-routine assignment."*

**The rule.** A photo's identity is `(camera_body, filename, EXIF DateTimeOriginal)`. The same physical shutter click cannot have produced two photos at two routine times. Therefore:

> **One physical photo → exactly one `media_packages.id` link in `media_photos`.** Any state that violates this is a bug to be quantified, fixed, and prevented at the matcher level *and* the DB level.

This is no longer "investigate and tighten." It is "enforce, and treat any violation as a P0 bug ticket."

**What changes:**

1. **Matcher emits at most one routine binding per photo.** `src/main/services/photos.ts` matcher: build the candidate-routines set for a photo, score, pick the single highest-scoring match, emit that one binding. If two routines tie (multiple windows actually overlap), log a `MATCH_CONFLICT` event with photo filename + camera + EXIF + both candidate routine windows. The matcher *never* emits both bindings.

2. **Tie-break rule, deterministic and stated.** When N routine windows cover a photo's EXIF time:
   - Prefer the routine whose window covers the EXIF time most-centrally (smallest `|exif - midpoint(window)|`).
   - If that ties, prefer the routine with the smaller window (more specific).
   - If that ties, prefer the routine with the lower `entry_number` (deterministic, audit-friendly).
   - Log every multi-candidate match at INFO with the candidate set and the chosen winner. Operator can post-event audit to identify schedule-window bugs.

3. **DB-level enforcement (CompPortal).** Add a partial unique index on `media_photos`:
   ```sql
   CREATE UNIQUE INDEX uniq_photo_per_competition
     ON media_photos (competition_id, camera_body, filename, captured_at)
     WHERE deleted_at IS NULL;
   ```
   The `(competition_id, camera_body, filename, captured_at)` tuple identifies a physical photo unambiguously. The partial index allows soft-deleted rows to coexist with the new row (preserving today's recovery flow). Any future INSERT that would create a second link silently `ON CONFLICT (...) DO NOTHING` — the second insert is a no-op, the first link wins. CompPortal-side `/plugin/complete` upserts already key on `(media_package_id, storage_url)` per `upload.ts:1209-1213`; this is a *narrower* invariant that prevents cross-routine duplication regardless of the upload path.

4. **Mid-flight detection in CSE.** When the matcher would assign a photo to a routine and the same `(camera_body, filename, captured_at)` is already in flight for a different routine in the same import run, detect and log; do not enqueue the duplicate.

5. **Quantify before/after.** Run an audit query *now*, before deploy, against current state for UDC Toronto + UDC London + every comp visible in `media_photos`:
   ```sql
   SELECT camera_body, filename, captured_at, COUNT(DISTINCT media_package_id) AS routine_count
     FROM media_photos
     WHERE deleted_at IS NULL AND competition_id = $1
     GROUP BY 1, 2, 3
     HAVING COUNT(DISTINCT media_package_id) > 1;
   ```
   Result is the size of the existing violation. Track this number to zero across the next 1–2 events.

6. **Cross-attribution cleanup pass (one-shot).** For each existing violation row from step 5: keep the link to the routine selected by the new matcher's tie-break rule (deterministic; can be computed offline against existing routine windows + take windows from item 2.8); soft-delete the other link(s). Bulk script, not interactive — runs against historical comps.

**The strict invariant is NOT:** "if the matcher emits a duplicate, suppress one." It is: **"the matcher must not emit a duplicate, and the DB must not store one even if some other path tries to."** Defense in depth.

**Where:**
- `src/main/services/photos.ts` matcher — single-binding emission + tie-break rule + `MATCH_CONFLICT` log + in-flight dedup. Pair with item **2.8** because the most likely *cause* of today's 4,519 cross-routine duplicates is take-window mutation on re-record (overlapping/inconsistent windows), which 2.8 directly fixes. 2.7 is the enforcement layer; 2.8 is the cause-removal layer. Audit the `/plugin/complete` insert path for `ON CONFLICT (camera_body, filename, captured_at, competition_id) DO NOTHING` semantics — verify it doesn't accidentally suppress legitimate new inserts. Test with the existing recovery flow.

**Risk + mitigation:**

## 2.8 — Immutable take-windows + take-aware matcher (re-record / extras correctness) [CSE+CP]

**Operator escalation 2026-04-27 10:45 EDT:** *"rerecording into a slot creates a massive issue for the photo matching… when we do any sort of extra routine recording or recording over a slot that video timestamps are preserved and the photo matching is intelligent to catch it. It's making a massive mess right now."*

**What:** The current data model has one `recordingStartedAt` / `recordingStoppedAt` per routine. Re-recording (or stopping + re-starting) overwrites them in place. Verified at `recording.ts:860-862` (`state.updateRoutineStatus(routine.id, 'recording', { recordingStartedAt: timestamp })`) — every `RECORDING STARTED` event clobbers the prior value with no archival. The post-stop matcher at `recording.ts:812-823` then asks `photos.rematchOrphansForWindow(routine.id, startedAt, stoppedAt)` using only the *current* (new) window. Any photo whose EXIF time fell in the *prior* take's window has no preserved window to match against, so it ends up:

- silently mis-attributed to whichever neighbouring routine's window the EXIF time happens to overlap, or
- left in the orphan drawer, or
- worst: linked to the new take's slot even though it was shot during the old take, polluting the published media package.

This is the correctness slice of redesign invariants 2 ("a take's recorded time window is IMMUTABLE"), 3 ("time window = canonical truth for photo-routine matching"), and 5 ("photos are matched additively"). The redesign defers a full schema rebuild to Phases 2 & 3 of the redesign doc; this item delivers the **correctness fix** without waiting for the schema rebuild — minimal-blast-radius take-window persistence + a matcher that reads all preserved windows for the routine.

**Concrete changes:**

1. **Persist every take's window on record-start, never overwrite.**
   - On each `handleRecordingStarted`, append a new `TakeWindow` record (rather than writing into a single field). Storage option (smallest blast radius): a sidecar JSON `<routineFolder>/_takes/<take_id>.json` containing `{takeId, recordingStartedAt, recordingStoppedAt|null, status: 'recording'|'completed'|'displaced', mkvPath, archivedToPath?}`. On stop, write `recordingStoppedAt` to the same file.
   - Mirror this state into `state.ts`'s persisted competition state under a new optional field `Routine.takes: TakeWindow[]` so it survives an app restart and shows up in the existing reconciler.
   - When a re-record displaces the prior take, the prior take's status becomes `'displaced'` *but its window is preserved*. The displaced `.mkv` either stays in the routine folder under `_archive/v1/<take_id>/` (today's behaviour, made consistent by Phase 4.3) or in the per-comp discard folder (redesign §3.3 once we get there). Either way the *window* lives in `_takes/<take_id>.json` and `Routine.takes`.
   - Same rules apply to **extras** (today's "extras at bottom of schedule"): every extra is a routine with its own `takes[]`. Recording onto an extra preserves its window with the same machinery.

2. **Matcher walks all preserved take-windows for a routine, not just the latest.**
   - `photos.rematchOrphansForWindow(routine.id, startedAt, stoppedAt)` is called with one window today. New API: `rematchOrphansForRoutine(routine)` reads `routine.takes[]` and rematches orphans whose EXIF time falls within ANY take's `[startedAt, stoppedAt]`. Match precedence: a photo binds to the take whose window covers its EXIF time. If multiple takes cover (rare; would mean overlapping records), bind to the latest take whose status is `'completed'` AND not `'discarded'`.
   - The cross-routine match (`photos.ts` window-vs-routine matcher) iterates `routine.takes[]` per routine instead of using the single `recordingStartedAt`/`recordingStoppedAt`. Implements redesign invariant 5 (additive matching) with no photo deletion.
   - Photos that bind to a `'displaced'` take: they were shot during that take. They stay linked to the take — and via the take, to the routine the take was *meant for*. If the operator later re-assigns the displaced take to a different routine (Phase 4 of the redesign), the photos travel with the take. **No photo is ever deleted; only relinked via the take's identity.**

3. **CompPortal-side mirror.** `media_packages` today has one `video_start_timestamp` and `video_end_timestamp`. The CSE-side `/plugin/complete` payload already sends these. We extend the payload to send a `takes: [{takeId, startedAt, stoppedAt, status, displaced: bool}]` array, and the CompPortal endpoint persists the array (new column `media_packages.takes JSONB` or a new `media_package_takes` table). The CompPortal photo→routine attribution path uses the same take-window precedence as CSE. Same scoring: a photo's `captured_at` matches a take, and the take's `media_package_id` is the routine link.

4. **Migration.** Existing `media_packages` rows have a single window. Treat as a single completed take with `takeId = media_package_id`. New events going forward populate `takes[]`. No retroactive backfill needed.

5. **Visibility.** A small chip / dropdown on the routine row shows `(N takes preserved)` when N>1. Clicking expands to show each take's start/stop time + status. This is a minimal version of redesign §4.4's row inspector — *enough to verify correctness*, not full UI.

**Where:**
- `src/main/services/recording.ts:850-863` — extend `handleRecordingStarted` to push a new TakeWindow, never overwrite.
- `src/main/services/recording.ts:780-825` — extend the post-stop block to write `recordingStoppedAt` onto the take, then call the new `rematchOrphansForRoutine(routine)`.
- `src/main/services/photos.ts:rematchOrphansForWindow` — keep as-is for back-compat; new entry `rematchOrphansForRoutine(routine)` walks `routine.takes[]`.
- `src/main/services/photos.ts` matcher — every site that reads `routine.recordingStartedAt` / `recordingStoppedAt` walks `routine.takes[]` instead. Build a single helper `getRoutineTakeWindows(routine): TakeWindow[]` and replace point-uses.
- `src/shared/types.ts` — add `TakeWindow` interface; add `takes?: TakeWindow[]` to `Routine`.
- `src/main/services/state.ts` — persist `takes` on routine save/load; migrate single-window legacy state to `takes: [{takeId: <legacy>, ...}]` on first read.
- New file `src/main/services/takes.ts` — the take-creation, take-displacement, take-list helpers. Pure functions over `Routine`.
- CompPortal: `/api/plugin/complete` route — accept and persist `takes[]`. Photo-attribution path on the CompPortal side reads `takes[]` for matching.

**Why:** operator escalation; verified active matcher bug at `recording.ts:860-862` and `recording.ts:816`. This is the correctness floor for any re-record or extra. Without it, every re-record continues to corrupt the photo↔routine attribution and produce multi-hour DB cleanup post-event (per post-mortem section **J**: R118/R119/R136/R140/R145/R146 cleanup on UDC Toronto Day 1; multi-hour task per affected routine).

This item also subsumes the photo-side correctness from redesign §6.3 ("photo ingest after a re-record") without requiring redesign Phase 2's schema choice (Option A/B/C from §7) to be decided first — `takes[]` lives on the existing `Routine` and `media_packages` rows; sibling-takes-as-separate-entries can be layered on later if/when the schema rebuild happens.

**Risk + mitigation:**
- *Risk: changing the matcher's window source breaks the existing single-window happy path.* → Mitigation: legacy routines auto-migrate to `takes: [{takeId: legacy, startedAt: routine.recordingStartedAt, stoppedAt: routine.recordingStoppedAt, status: 'completed'}]` on first read. Matcher's behaviour for never-re-recorded routines is identical.
- *Risk: `_takes/*.json` sidecars get out of sync with `Routine.takes` in app state.* → Mitigation: Routine.takes is authoritative for the matcher; `_takes/*.json` is forensic backup only. On boot, reconcile pass repopulates Routine.takes from any sidecars whose `take_id` isn't already in state (additive only — no deletion of state-only takes).
- *Risk: photos that fell in the gap between two takes (e.g., between a stop and a re-record) silently orphan.* → Mitigation: that's already the current behaviour; not a regression. Phase 3's slideshow + Phase 1's banner make it visible. Phase 4's redesign Phase 2 will offer the operator a "re-bind orphan to nearest take" UI; for now, orphans land in the orphan drawer (existing surface).
- *Risk: CompPortal-side change creates a schema migration window where old/new payloads coexist.* → Mitigation: new `takes[]` column is additive; old `video_start_timestamp` / `video_end_timestamp` stay until backfill is verified. Old client payloads (no `takes[]`) get the legacy single-take treatment.

### NEW — Tier 2: opportunistic deep audio audit [P1]

**5.3.2 — `silencedetect` between-takes pass on encoded MP4s.**

**What:**
- Run ffmpeg `silencedetect=noise=-50dB:d=10` on each encoded MP4 → list of silent regions ≥ 10s.
- Sum silence-duration per file. If any judge has > 50% silent for the routine, flag.
- Banner format: *"R199 J1 audio: 312 of 505 sec silent. Re-record?"*

**Scheduling — opportunistic, not periodic:**
- Track gap between operator's last STOP and next START_RECORD.
- Run silencedetect ONLY when gap ≥ 30s AND encode queue depth = 0. Defer otherwise.
- Result lands when it lands (could be immediate, could be next break). Banner posts whenever.
- Naturally rate-limits to operator tempo; rushed back-to-back routines get tier 1 only.

**Where:**
- New file `src/main/services/audioAudit.ts` — orchestrates silencedetect runs + gap tracking.
- Subscribe to `recording.stopped` and `recording.started` events to maintain gap timer.
- Reuse the existing ffmpeg path resolver in `src/main/services/ffmpeg.ts`.

**Cost:**
- ~7s wall-clock per routine on free CPU (4 files run parallel via existing ffmpeg infra).
- During quiet 30-90s gaps: ~25% of one core for ~7s. Negligible.
- Zero CPU during live takes (gated by gap-check).

**Catches:** intermittent mid-routine dropouts (judge mic flat 2 min then back) that tier 1's whole-file ratio averages out.

**Testable signal:** on a routine where ASIO drift caused a 60s silence in the middle, banner fires after the next operator break (gap ≥ 30s).

**Effort:** S–M (~1.5 days, including silencedetect output parsing + gap-tracking).
