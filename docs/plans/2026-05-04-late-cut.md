# Late Cut — recovery flow for missed routine boundaries

**Captured:** 2026-05-04 11:35 EDT
**Status:** Spec locked, NOT YET IMPLEMENTED
**Owner:** next-break list

## Problem

Operator forgets to advance to the next routine. Recording continues across two routines (e.g., 100 + first 10-30s of 101) producing one merged file and zero file for routine 101. Bleed durations are typically 10-30s. Operator policy is **never stop a recording mid-routine once it's started** — so traditional stop-and-restart recovery is off-limits.

## Solution shape

When operator notices the bleed mid-101, a single button + chord lets them mark "the cut should have happened N seconds ago." App snaps to nearest silence, splits state immediately, and at the end of the recording (next NEXT press) the encoder produces two clean files in the correct slots. Full app flow resumes.

## UX

- **Trigger:** "Late Cut" button in the record panel (`Controls.tsx`). NO Stream Deck button.
- **Popover:** non-blocking, anchored bottom-right (similar treatment to `ReassignPopover`). Recording continues uninterrupted behind it.
- **Chord buttons:** `-5s` / `-10s` / `-15s` / `-20s` / `-30s` / `Custom` / `Cancel`.
- **Custom:** small numeric input (seconds, max 120).
- **After pick:** popover dismisses, heads-up row appears in RoutineTable showing "Late cut at HH:MM:SS — routine 100 ends here, 101 starts. [Undo]" — auto-hides at 5s, undo locks out at 5s.

## Behavior on press

1. Cut point = `now − N seconds` (UTC clock) — operator's exact estimate, no audio refinement yet
2. **State writes (atomic, persisted to `state.json` immediately):**
   - `routines[curIdx].end_ts = cutPoint`
   - `routines[curIdx].recordingSplitAt = cutPoint`
   - `routines[curIdx + 1].start_ts = cutPoint`
   - `take.lateCutPoint = cutPoint` (operator's estimate; refined at encoding time — see below)
   - `take.lateCutEstimateOnly = true` (flag indicating cut hasn't been silence-snapped yet)
3. **Routine pointer advances** one step (100 → 101). LT broadcast updates so the live audience sees correct routine info from the cut moment onward.
4. **Heads-up row** shown for 5s with Undo.

## Audio-snap (deferred to encoding time — AMENDMENT 2026-05-04)

The recording is active-not-closed when operator hits Late Cut. OBS hasn't yet flushed the most recent 2-5s of audio to disk — exactly the window we need to snap on. Snapping at button-press time would either fail to find silence (falls back to operator's exact second, defeats the purpose) or produce stale results from older audio.

**Decision:** snap runs at end-of-recording, just before the ffmpeg split. By then the file is closed and full audio is readable.

**Snap algorithm:**
1. Read audio of the closed recording file from `[lateCutPoint - 5s, lateCutPoint + 5s]`
2. Find the longest contiguous silence (>1s, RMS below -50dBFS)
3. If found, refine `take.lateCutPoint` to the centre of that silence; refine `routines[curIdx].end_ts` and `routines[curIdx + 1].start_ts` to match
4. If not found, honor operator's exact seconds; log warning
5. Update heads-up: "Late cut snapped to HH:MM:28.4 (silence detected)" or "Late cut at operator estimate HH:MM:30.0 (no silence found)"
6. Clear `take.lateCutEstimateOnly`

UI behavior: operator's selected `-10s` shows immediately on press. Heads-up row updates to refined value once encoding starts (typically within 1-2s of NEXT press).

## At end of recording (operator hits NEXT)

1. Recording stops normally (existing flow).
2. Encoder detects `take.lateCutPoint` set → runs ffmpeg twice with `-c copy`:
   - `ffmpeg -ss <recStart> -to <cutPoint> -i input -c copy → routine100.mp4`
   - `ffmpeg -ss <cutPoint> -i input -c copy → routine101.mp4`
3. Both files placed in normal slot paths. Encoding pipeline completes.
4. **Photo matcher re-runs** on photos in the affected window — re-buckets by EXIF time vs new boundaries.
5. **Upload pipeline** picks up both routines automatically.
6. Routine pointer was already at 101; standard NEXT advances to 102 and starts new recording for 102. **Net effect: NEXT skips over what would otherwise have been the 101 advance** — that work is already done.

## Undo (within 5s grace window)

- Reverts state changes
- Clears `take.lateCutPoint`
- Rolls back routine pointer (101 → 100)
- Restores LT broadcast info
- Heads-up dismisses

After 5s the cut commitment locks; operator must wait for end-of-routine and re-edit if wrong.

## Edge cases

- **Recording stopped before late-cut applied** → different code path: retroactive split on closed file (no live state to roll forward, just the file split).
- **Cut requested earlier than recording start** → clamp to recording start, warn via toast.
- **Cut requested while recording is OFF** → toast error, no-op.
- **Operator double-clicks chord rapidly** → debounce, take latest pick.
- **Operator requests another late-cut on the same take after first one applied** → blocked in v1 (no multi-cut stack). Toast: "Late cut already applied to this take. Wait for next routine."
- **Audio-snap finds no silence within ±5s** → honor exact second, log warning.

## Out of scope (v1)

- **No multi-cut stack** — single cut per take only. If operator missed two transitions, they handle one via late-cut and the other manually (existing flow).
- **No Stream Deck button** — app button only.
- **No Android tablet button** — app only.
- **No live waveform scrub UI** — chord-only. Could add later if operator wants more precision.
- **No proactive auto-detect prompt** — purely operator-initiated.
